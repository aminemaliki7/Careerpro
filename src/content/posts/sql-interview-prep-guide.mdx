## The Real Test

You're in an interview. The question: "Find the second highest salary."

You write this and feel confident:
```sql
SELECT MAX(salary) 
FROM employees 
WHERE salary < (SELECT MAX(salary) FROM employees);
```

Then they ask: "What if there are millions of employees and this runs constantly?"

This is where most candidates freeze. The interview isn't about syntax—it's about understanding how databases work.

## The 4 Concepts That Actually Matter

### 1. Indexes (And When NOT to Use Them)

Everyone says "indexes make queries faster." But when do they make things slower?

Indexes speed up reads but slow down writes. They help with WHERE, JOIN, and ORDER BY. But adding them everywhere is counterproductive, and sometimes a full table scan is actually faster.

**The interview question:** "Search is slow on 10 million rows. What do you do?"

**Junior answer:** "Add an index."

**Senior answer:** "Check the execution plan first. If it's a column with only 5 distinct values, an index won't help. I'd also check existing indexes and if we're returning too much data."

That's the difference.

### 2. JOINs and NULL Behavior

You know INNER and LEFT JOIN. But NULL behavior trips up most candidates.

**Critical insight:** LEFT JOIN with WHERE vs LEFT JOIN with ON are different things. The placement of your condition completely changes the results.

**Common question:** "Find users who never ordered product ID 123."

```sql
SELECT u.user_id, u.name
FROM users u
LEFT JOIN orders o ON u.user_id = o.user_id
LEFT JOIN order_items oi ON o.order_id = oi.order_id 
  AND oi.product_id = 123
WHERE oi.order_item_id IS NULL;
```

Then they ask: "What about users who never placed ANY order?"

If you spot that this query incorrectly includes them and can fix it, you're ahead of 80% of candidates.

### 3. Window Functions

If you don't know window functions, you'll struggle in mid-level interviews. They're essential, not advanced.

Window functions let you rank, calculate running totals, and compare rows without collapsing them into groups.

That "second highest salary" question? Here's the senior answer:

```sql
SELECT DISTINCT salary
FROM (
  SELECT salary, 
         DENSE_RANK() OVER (ORDER BY salary DESC) as rank
  FROM employees
) ranked
WHERE rank = 2;
```

Handles ties, performs better, more readable. Learn ROW_NUMBER, RANK, DENSE_RANK, and LEAD/LAG. These separate junior from senior developers.

### 4. Reading Execution Plans

Interviewers show you a slow query. Can you diagnose it?

They're checking if you can read EXPLAIN output, spot table scans where indexes should be used, and identify unnecessary subqueries.

**Example slow query:**
```sql
SELECT p.product_name, COUNT(*) as order_count
FROM products p
WHERE p.product_id IN (
  SELECT oi.product_id 
  FROM order_items oi
  WHERE oi.created_at > '2025-01-01'
)
GROUP BY p.product_name
ORDER BY order_count DESC;
```

**Better version:**
```sql
SELECT p.product_name, COUNT(*) as order_count
FROM products p
INNER JOIN order_items oi ON p.product_id = oi.product_id
WHERE oi.created_at > '2025-01-01'
GROUP BY p.product_id, p.product_name
ORDER BY order_count DESC
LIMIT 10;
```

The subquery executes for every product. The JOIN is more efficient. Can you explain why? That's what they're listening for.

## The Mistakes That Cost Offers

**Using SELECT *.** Always specify columns. It shows you think about performance and maintainability.

**Forgetting transactions.** When updating related tables, do you wrap it in BEGIN/COMMIT? What happens if one fails?

**Not handling NULLs.** Remember: `WHERE column != 'value'` excludes NULLs. Use `IS NULL`, not `= NULL`. Know that `COUNT(column)` excludes NULLs but `COUNT(*)` doesn't.

**Not asking questions.** When given a problem, ask about data volume, query frequency, and acceptable response time. This shows real-world thinking.

## For Moroccan Developers

European clients (common in nearshoring) typically use PostgreSQL. Know the differences from MySQL—especially around JSON support and transaction behavior.

French companies particularly value data integrity. Be ready to discuss constraints and ACID properties.

## How to Actually Prepare

Don't just read. Set up PostgreSQL with sample data and write queries. The Sakila database is perfect for practice.

Learn to read execution plans. Run EXPLAIN on everything. This single skill sets you apart in interviews.

Solve each problem multiple ways. Write three different queries for the same result, then analyze which is best and why.

Build something real. Create a project that needs complex queries. Interview questions feel different when you've solved similar problems in production.

## The Night Before

Review these from memory:
- A query with multiple JOINs
- A query using DENSE_RANK or ROW_NUMBER  
- A query with GROUP BY and HAVING
- A query using CASE for conditional logic

More importantly: sleep. SQL interviews test clear thinking under pressure.

## The Real Secret

Interviewers aren't trying to trick you. They want to see how you think, whether you ask good questions, if you understand tradeoffs, and how you communicate reasoning.

The best candidates aren't the ones who know the most SQL. They're the ones who think clearly and explain their approach.

When you can explain not just WHAT a query does but WHY it's written that way, you're ready.
